# LabAid InsureTech Platform Constitution

## Core Principles

### I. Proto-First Contract Design (NON-NEGOTIABLE)

All service boundaries, DTOs, and domain events MUST be defined as Protocol Buffer
(`.proto`) files under `proto/insuretech/` **before** any service, portal, or SDK
implementation begins. Generated artifacts (`gen/`) and the OpenAPI view (`api/`) are
downstream products of proto; they MUST NOT diverge from the source of truth.

**Contract rules:**
- Proto packages follow `insuretech.<domain>.<layer>.v<N>` naming
  (e.g., `insuretech.policy.services.v1`).
- New field numbers are append-only; existing field numbers MUST NEVER be reused or removed
  within a major version.
- `buf lint` and `buf breaking --against .git#branch=main` MUST pass in CI on every
  proto-touching commit; failures BLOCK merge.
- Breaking-change scope is FILE; `buf.yaml` lint ruleset is STANDARD.

**Generation pipeline (authoritative order — `scripts/generate.ps1`):**

```
proto/insuretech/**/*.proto
  │
  ▼  buf generate (buf.gen.yaml)
  │   ├─ protocolbuffers/go   → gen/go/   (.pb.go + _grpc.pb.go)
  │   ├─ bufbuild/es          → gen/ts/   (.pb.ts)
  │   └─ protocolbuffers/csharp → gen/csharp/ (.cs stubs)
  │
  ▼  scripts/inject_gorm_tags.go  (auto-derives or reads @inject_tag comments)
  │   └─ writes gorm:"..." struct tags into gen/go/**/*.pb.go
  │      Header: // Code generated by inject_gorm_tags.go. DO NOT EDIT.
  │
  ▼  api/generator/main.py   (buf build → descriptors.pb → parse HTTP annotations)
  │   └─ writes api/openapi.yaml  (OpenAPI 3.0+ — authoritative REST contract)
  │
  ▼  SDK generation from api/openapi.yaml
      ├─ TypeScript client → sdks/ts/
      ├─ Swift client      → sdks/swift/
      ├─ Kotlin client     → sdks/kotlin/
      └─ C# client         → sdks/csharp/
```

- Running `scripts/generate.ps1` (or `scripts/generate.sh` on Linux/macOS) MUST produce all
  of the above in one command; partial generation is a CI failure.
- CI MUST gate on: buf lint ✓, buf breaking ✓, `*.pb.go` timestamp newer than `*.proto`,
  `api/openapi.yaml` regenerated (diff check), SDK outputs regenerated.

**GORM model exclusivity (NON-NEGOTIABLE):**
- Proto-generated `.pb.go` files with injected GORM tags are the ONLY permitted GORM models.
- Hand-crafted Go structs used as GORM models are FORBIDDEN; delete and replace with proto-gen.
- GORM tags are injected via `scripts/inject_gorm_tags.go` either automatically (from
  `json:"."` + `protobuf:"..."` tags) or explicitly via trailing comment:
  ```go
  // @inject_tag: gorm:"column:policy_id;primaryKey;type:uuid"
  ```
- GORM options that cannot be expressed via `@inject_tag` MUST be encoded as proto custom
  options (`(check_constraint)`, `(db_column)`) defined in `proto/insuretech/common/`.
- Serializers for complex fields (e.g., `Money`, embedded message lists) MUST be declared
  in the GORM tag; the injector upgrades existing tags to add missing serializers.

**OpenAPI & SDK template customisation:**
- HTTP bindings for every RPC MUST use `google.api.http` annotations directly in proto;
  undocumented RPCs MUST still carry a `// @exclude_from_openapi` comment if intentionally
  omitted.
- The OpenAPI generator reads description templates from `api/descriptions/` and
  `api/generator/doc_templates.py`; custom descriptions are written there — NOT by
  hand-editing `api/openapi.yaml`.
- SDK templates are stored in `api/generator/` and MUST NOT be modified for per-feature
  customisation; use template variables or proto annotations instead.
- Generated SDKs (`sdks/`) are committed artifacts consumed by portals and mobile apps;
  they are never hand-edited.
- Generated stubs (`gen/csharp/`, `gen/go/`, `gen/ts/`, `sdks/`) carry
  `DO NOT EDIT` headers; any file missing this header in those directories is a CI warning.

### II. Polyglot Service Ownership (NON-NEGOTIABLE)

Each language runtime owns its designated domain layer and MUST NOT assume responsibility
for another layer's concerns.

| Runtime | Domain Ownership |
|---------|-----------------|
| **Go 1.22+** | Gateway, AuthN, AuthZ, KYC, Partner, B2B, Fraud, Payment, Notification, Workflow, DocGen, Storage, IoT, Analytics infra, DBManager |
| **C# .NET 8 (PoliSync)** | Insurance domain logic — Product, Quote, Order, Commission, Policy, Underwriting, Claims, Endorsement, Renewal, Refund |
| **TypeScript / Next.js 16** | Web portals (B2B, Customer, System) — BFF layer only; no direct DB access |
| **Swift / Kotlin** | Native iOS/Android clients — consume typed REST SDK only; no direct gRPC calls |
| **Python** | AI Engine and OCR/PDF processing only |

- C# MUST NOT own a PostgreSQL schema; all persistence is delegated to Go `insurance-service`
  (:50115) via gRPC data gateway interfaces.
- TypeScript portals communicate exclusively through `app/api/` BFF routes using typed SDK wrappers.
- Mobile clients MUST use JWT auth; portals MUST use server-side sessions.
- Cross-runtime logic sharing happens only through proto contracts and Kafka domain events —
  never through shared libraries or direct DB cross-access.

### III. REST API Design Standard — Noun-Based, OpenAPI 3.0+ (NON-NEGOTIABLE)

All HTTP APIs exposed externally MUST conform to OpenAPI 3.0+ with strict noun-based
resource paths and snake_case conventions. See Principles XIII–XX for the detailed
normative rules covering envelope, status codes, errors, security, pagination, DI
contract, naming, and null handling.

**Path design:**
- Resources are plural nouns with hierarchical nesting:
  `/v1/policies`, `/v1/policies/{policy_id}/claims`,
  `/v1/organizations/{org_id}/members`.
- HTTP verbs encode intent: `GET` = idempotent read, `POST` = create,
  `PUT` = full replace, `PATCH` = partial update, `DELETE` = remove.
- Verb paths are FORBIDDEN: `/v1/createPolicy`, `/v1/policy/approve`.
  Use colon-action notation (Google AIP-136) instead:
  `POST /v1/policies/{id}:cancel`, `POST /v1/claims/{id}:approve`.
- Path segments: `kebab-case`. Path parameters: `snake_case` (`{policy_id}`).
- Nesting MUST NOT exceed 2 levels (`/v1/claims/{claim_id}/documents` — flatten deeper).

**Query parameters** (snake_case, standardised across all list endpoints):

| Parameter | Meaning | Default |
|-----------|---------|---------|
| `page` | Page number (1-based) | 1 |
| `page_size` | Records per page (max 100) | 20 |
| `sort_by` | Field name to sort by | — |
| `sort_order` | `asc` or `desc` | `desc` |
| `search` | Full-text search query | — |

**Response envelope** (all endpoints — see Principle XIII for full schema):
```json
{ "success": true, "data": {}, "error": null, "meta": { "request_id": "...", "timestamp": "..." } }
```

**Error responses** — see Principle XV for full schema. Error bodies use the standard
`{ success, data, error, meta }` envelope with `success: false` and `error` populated;
RFC 7807 fields MUST NOT be used.

**Versioning:** Breaking changes require a new URL prefix (`/v2/`) with a minimum
6-month deprecation notice using `Deprecation` and `Sunset` response headers.

### IV. Event-Driven Domain Communication

All cross-domain state changes MUST be propagated via Kafka domain events using
canonical topic naming and the transactional outbox pattern.

- Topic format: `insuretech.<domain>.v<N>.<EventName>`
  (e.g., `insuretech.payment.v1.PaymentCompleted`).
- Events MUST be defined as proto messages under the domain's `events/` proto package.
- Producers MUST use the transactional outbox pattern; direct Kafka publish without
  outbox is FORBIDDEN for critical domain events.
- Consumers MUST be idempotent — duplicate delivery MUST NOT cause double-processing.
- Dead-letter topics (`*.dlq`) MUST be monitored; unacknowledged DLQ messages
  trigger on-call alert within 15 minutes.
- Event schema evolution follows proto backward-compatibility rules; breaking event
  changes require a new topic version.

### V. Zero-Trust Security & Regulatory Compliance (NON-NEGOTIABLE)

The platform operates under a zero-trust model and MUST maintain full IDRA and
BFIU/AML-CFT regulatory compliance at all times.

- Every gateway-routed request MUST pass AuthN token validation then AuthZ permission
  check; no anonymous access to protected resources.
- All PII (NID, phone, medical data) MUST be encrypted at rest with AES-256-GCM;
  keys managed through AWS KMS / Azure Key Vault with 90-day rotation.
- Passwords MUST use Argon2id. MD5, SHA-1, and bare bcrypt are FORBIDDEN.
- TLS 1.3 is the minimum transport standard; TLS 1.2 only with documented partner exception.
- IDRA statutory reports (Forms IC-1, IC-2, IC-3, IC-4, FCR/CARAMELS) MUST be auto-generated
  on schedule via the report pipeline — late generation is a compliance breach.
- AML/CFT rules (8 mandatory trigger categories per SEC-017) MUST fire automatically;
  SAR SLA: compliance review within 24 hours, BFIU submission within 3 business days.
- PCI-DSS SAQ-A: card data MUST NOT be stored; redirect/hosted payment page model only.
- SAST (SonarQube / Checkmarx) runs on every commit; CRITICAL findings block merge.
- OWASP Top-10 controls and ClamAV virus scanning on all file-upload paths are mandatory baselines.
- API rate limiting: 1,000 req/hour authenticated, 100 req/hour anonymous (per user/IP).

### VI. Vertical Slice Architecture & Test Discipline

Every microservice MUST organise code by business-capability slices (VSA). Tests follow
Red-Green-Refactor and MUST precede implementation.

- Each feature slice contains handler, domain logic, repository/gateway call, and validation
  as a cohesive unit; cross-slice state access is via service interface only.
- Tests MUST be written (failing) before any implementation for new RPCs or endpoints.
- Unit test coverage MUST reach ≥ 80% for all services.
- Integration tests MUST cover: new gRPC contract paths, Kafka consumer/producer pairs,
  data-gateway round-trips, and security-relevant flows.
- Testcontainers MUST be used for tests requiring PostgreSQL, Kafka, or Redis;
  mocking infrastructure in integration tests is FORBIDDEN.
- xUnit + Moq for C#; standard `testing` + testcontainers-go for Go; Jest / Vitest for TypeScript.

### VII. Observability & Operational Readiness

All services MUST be production-observable before promotion out of staging.

- Structured JSON logging with `request_id` and `tenant_id` on every log line
  (zap for Go; Serilog for C#; pino for TypeScript).
- OpenTelemetry traces and spans on all gRPC handlers and HTTP endpoints; W3C
  `traceparent` header MUST propagate across every service boundary.
- Prometheus RED metrics (Rate, Error, Duration) MUST be exposed on `/metrics`.
- Grafana dashboards MUST exist per service domain before production promotion.
- Health probes: `GET /healthz` (liveness) and `GET /readyz` (readiness) are mandatory
  on every HTTP-serving service.
- SLOs: p95 < 500 ms for policy/claims operations; p95 < 200 ms for search endpoints.
  Violations trigger automated alerts (PagerDuty / Alertmanager).

### VIII. Multi-Tenancy & Data Isolation

The platform MUST enforce strict tenant isolation at every layer — schema, API, event,
and UI.

- Every database row belonging to a tenant MUST carry a non-nullable `tenant_id` column;
  repository queries MUST filter by `tenant_id` in every read path.
- Row-level tenant scoping MUST be enforced in GORM scopes (Go) and EF Core query filters (C#);
  ad-hoc tenant bypass is FORBIDDEN.
- JWTs and API keys MUST embed a `tenant_id` claim; the gateway validates tenant context
  on every inbound request.
- Cross-tenant reads are permitted only for the System Admin role and MUST produce an
  immutable audit log entry.
- Tenant provisioning and teardown MUST be atomic (saga/compensating transactions);
  partial-state tenants MUST be auto-detected and flagged for remediation.

### IX. Versioning & Backward Compatibility

All public contracts — proto, REST API, Kafka events, SDKs — MUST maintain backward
compatibility within a declared major version.

- Semantic versioning (MAJOR.MINOR.PATCH) applies to proto packages, REST URL prefixes,
  client SDKs, and this constitution.
- MAJOR: breaking change (field removal or renaming, RPC removal, HTTP path removal).
- MINOR: additive change (new field, new optional RPC, new endpoint, new optional param).
- PATCH: bug fix, wording clarification, non-semantic refinement.
- Deprecated proto fields MUST carry `[deprecated = true]`; deprecated REST endpoints MUST
  return `Deprecation` and `Sunset` headers for a minimum 6-month window before removal.
- SDK major-version changes MUST be accompanied by a published migration guide before
  the updated client is shipped.

### X. Simplicity & YAGNI

Implementation MUST solve the problem at hand; anticipatory complexity is rejected.

- No new abstractions, utilities, or framework layers created for hypothetical future needs.
- New microservice boundaries require explicit justification; consolidation is preferred
  over service proliferation.
- External dependencies require a documented rationale; supply-chain risk MUST be assessed
  before adoption.
- Generated code artefacts (`gen/`) MUST be regenerated via CI; manually maintained
  parallel type definitions are FORBIDDEN.

### XI. Hybrid SQL Migration Contract (NON-NEGOTIABLE)

Proto is the **sole schema definition authority**. SQL files are a thin execution
vehicle for schema evolution only — they MUST NOT define structure or seed data.

**What SQL migration files MAY contain (path: `backend/inscore/db/migrations/`):**

| Allowed | Forbidden |
|---------|-----------|
| `ALTER TABLE … ADD COLUMN` for columns that already exist in the proto-gen model | `CREATE TABLE` |
| `ALTER TABLE … ALTER COLUMN` to sync type/constraint drift auto-detected by the engine | `DROP TABLE` |
| `CREATE INDEX` / `DROP INDEX` for performance | `INSERT` / `UPDATE` / `DELETE` |
| `ALTER TABLE … ADD CONSTRAINT` / `DROP CONSTRAINT` | `ADD COLUMN` that is NOT already in proto |
| Comments | Any DDL that creates net-new schema not reflected in proto |

- The DBManager (`backend/inscore/cmd/dbx/`) is the only runtime that executes
  migrations: `run_migration.ps1 --Target=primary`.
- Direct SQL execution for inspection only: `./dbx.exe sql --sql="SELECT 1" --target=primary`.
- **Seeders** (reference / bootstrap data) live exclusively in
  `backend/inscore/db/seeds/`; seed files MUST only contain `INSERT … ON CONFLICT DO NOTHING`
  or `INSERT … ON CONFLICT DO UPDATE` statements — never structural DDL.
- The migration engine MUST enforce these rules programmatically:
  - Parse every `.sql` file at migration-plan time; reject files containing forbidden keywords
    (`CREATE TABLE`, `DROP TABLE`, `INSERT`, `UPDATE`, `DELETE` outside seeds/) with a
    non-zero exit and a clear error message.
  - **Code freshness gate**: block migration execution if any `*.pb.go` file in `gen/go/` is
    older than its corresponding `*.proto` source; developer MUST run `scripts/generate.ps1`
    first.
  - **Zombie column detection**: after each migration run, compare DB columns against
    proto-derived column set; log WARNINGs for zombie columns (present in DB, absent in proto)
    and FAIL with `--strict` flag.
  - **Type sync**: auto-generate compensating `ALTER TABLE … ALTER COLUMN TYPE` statements
    when a proto field type change is detected; log and require explicit approval before
    applying.
  - **Constraint drift**: auto-repair FK `ON DELETE`, `NOT NULL`, and `CHECK` rules to
    match proto annotations; log each repair.

**DB naming rules (from `rules/dbrules.md`):**
- Primary key: `{entity}_id` (e.g., `policy_id`, `tenant_id`) — generic `id` is FORBIDDEN.
- Foreign key: `{referenced_entity}_id`.
- Table names: `snake_case`, plural (e.g., `policy_riders`, `fraud_alerts`).
- Column names: `snake_case`.
- Index names: `idx_{table}_{columns}` (e.g., `idx_policies_customer_status`).
- Constraint names: `chk_{table}_{column}`.
- Every entity MUST store `audit_info` as a JSONB column.
- Every `Money` proto field MUST have a companion `{field}_currency` column.
- `CHECK` constraints MUST be declared via proto `(check_constraint)` option, not free-form SQL.

**Schema drift CI gate:** `run_migration.ps1 --dry-run --strict` MUST pass in CI;
unexpected drift (zombie columns or type mismatches) fails the pipeline.

### XIII. Response Envelope Standard (NON-NEGOTIABLE)

Every API response — success or error — MUST use the standard envelope.
Applies to all 34 services across all client platforms (iOS, Android, Web, SDKs).

**Canonical schema:**
```json
{
  "success": true | false,
  "data": { ... } | null,
  "error": { ... } | null,
  "meta": {
    "request_id": "req_abc123",
    "pagination": { ... } | null,
    "timestamp": "2024-01-15T10:30:00Z",
    "api_version": "v1"
  }
}
```

**Invariants:**
- `success: true` → `data` carries the payload; `error` MUST be `null`.
- `success: false` → `data` MUST be `null`; `error` carries the error object.
- `data` MAY be `null` on success for fire-and-forget action endpoints (logout, cancel, etc.).
- `error` MUST be `null` on any `2xx` response — clients MUST NOT inspect `error` on a 2xx.
- HTTP status codes are the authoritative success/failure signal; `success` MUST mirror them.

**OpenAPI component schemas (authoritative):**

```yaml
ApiResponse:
  type: object
  required: [success]
  properties:
    success:
      type: boolean
    data:
      nullable: true
    error:
      $ref: '#/components/schemas/Error'
      nullable: true
    meta:
      $ref: '#/components/schemas/ResponseMeta'
      nullable: true

ResponseMeta:
  type: object
  properties:
    request_id:
      type: string
    pagination:
      $ref: '#/components/schemas/PaginationMeta'
      nullable: true
    timestamp:
      type: string
      format: date-time
    api_version:
      type: string
```

- The `error` field MUST NOT appear inside any success response schema (`*Response`,
  `*Data`, etc.); remove it from all domain-level schemas.
- The envelope is mandatory even for `DELETE 204` (which carries no body at all); the
  204 case is the only exception where the envelope is absent.

### XIV. HTTP Status Code Standards (NON-NEGOTIABLE)

**Decision logic:**

```
POST /resource          → Creating a new persistent resource?    YES → 201 Created
                                                                 NO  → 200 OK
GET  /resource          → 200 OK
GET  /resource/{id}     → 200 OK (404 if not found)
PUT  /resource/{id}     → 200 OK
PATCH /resource/{id}    → 200 OK
DELETE /resource/{id}   → 204 No Content (no body)
POST /resource/{id}:action → 200 OK
```

**Full reference:**

| Code | Name | When to Use |
|------|------|------------|
| 200 | OK | Successful GET; successful action POST; successful PUT/PATCH |
| 201 | Created | POST creating a new persistent resource |
| 204 | No Content | DELETE; fire-and-forget with no confirmation needed |
| 400 | Bad Request | Malformed JSON; missing required fields; wrong types |
| 401 | Unauthorized | No token; expired token; invalid token |
| 403 | Forbidden | Valid token but insufficient permissions |
| 404 | Not Found | Resource does not exist |
| 409 | Conflict | Resource already exists; version conflict |
| 422 | Unprocessable Entity | Valid JSON but business validation failed |
| 429 | Too Many Requests | Rate limit exceeded |
| 500 | Internal Server Error | Unexpected server error |
| 503 | Service Unavailable | Downstream service unavailable |

**POST verb classification (resource creation → 201):**

RPC names starting with any of these verbs create a new persistent resource and MUST return 201:
`Create`, `Register`, `Submit`, `Initiate`, `Request`, `Add`, `Upload`, `Start`,
`Open`, `File`, `Issue`, `Generate` (when producing a new document/report resource).

RPC names starting with these verbs perform an action and MUST return 200:
`Verify`, `Validate`, `Approve`, `Reject`, `Cancel`, `Revoke`, `Activate`, `Deactivate`,
`Assign`, `Send`, `Check`, `Calculate`, `Process`, `Handle`, `Complete`, `Confirm`,
`Run`, `Execute`, `Rotate`, `Refresh`, `Login`, `Logout`, `Change`, `Reset`, `Renew`,
`Settle`, `Reconcile`, `Review`, `Discontinue`, `Mark`, `Enable`, `Disable`, `Batch`,
`Sync`, `Trigger`, `Schedule`, `End`, `Close`, `Archive`, `Restore`, `Suspend`, `Resume`.

Path segments containing `:` (colon-action notation) always return 200.

**400 vs 422 mandatory distinction — both MUST be declared on every write endpoint:**

| Code | Trigger |
|------|---------|
| 400 | Malformed request — cannot parse (invalid JSON, wrong Content-Type) |
| 422 | Valid request — business rule failed (duplicate email, invalid premium, NID rejected) |

**201 Created MUST include a `Location` header:**
```
HTTP/1.1 201 Created
Location: /v1/policies/pol_abc123
```

**204 No Content carries no body whatsoever** — the envelope is absent; clients MUST
expect an empty response and not attempt to parse it.

**Required error codes per endpoint type:**

| Code | Required For |
|------|-------------|
| 400 | All endpoints |
| 401 | All authenticated endpoints |
| 403 | All authorised endpoints |
| 404 | Endpoints with path parameters referencing a resource |
| 409 | POST endpoints that may produce duplicates |
| 422 | All POST/PUT/PATCH endpoints |
| 429 | All public-facing endpoints |
| 500 | All endpoints |

### XV. Error Handling Standards (NON-NEGOTIABLE)

Errors NEVER live inside success response schemas. Errors arrive exclusively via
HTTP 4xx/5xx status codes with the standard error envelope.

**Canonical Error schema:**

```yaml
Error:
  type: object
  required: [code, message]
  properties:
    code:
      type: string
      description: Machine-readable UPPER_SNAKE_CASE, domain-prefixed error code.
    message:
      type: string
      description: Human-readable, locale-safe message suitable for UI display.
    field_violations:
      type: array
      description: Field-level violations for 422 responses.
      items:
        $ref: '#/components/schemas/FieldViolation'
    error_id:
      type: string
      description: Unique error instance ID (format: err_{uuid}) for support lookup.
    retryable:
      type: boolean
      description: true = retry may succeed; false = retry will not help.
    retry_after_seconds:
      type: integer
      description: Seconds before retry. Set only when retryable=true.
    documentation_url:
      type: string
    http_status_code:
      type: integer

FieldViolation:
  type: object
  required: [field, message]
  properties:
    field:
      type: string
      description: Dot-notation for nested ("address.city"), bracket for arrays ("items[0].amount").
    message:
      type: string
    code:
      type: string
      description: Machine-readable violation code (REQUIRED, TOO_SHORT, INVALID_FORMAT, etc.)
    rejected_value:
      type: string
```

**Error code naming convention** — all codes MUST be `UPPER_SNAKE_CASE` and domain-prefixed:

```
AUTH_INVALID_CREDENTIALS   AUTH_TOKEN_EXPIRED   AUTH_ACCOUNT_LOCKED
AUTH_OTP_EXPIRED           AUTH_OTP_ALREADY_USED

POLICY_NOT_FOUND           POLICY_ALREADY_CANCELLED  POLICY_RENEWAL_NOT_ALLOWED
PAYMENT_INSUFFICIENT_FUNDS PAYMENT_GATEWAY_TIMEOUT   PAYMENT_METHOD_NOT_FOUND
CLAIM_ALREADY_SETTLED      CLAIM_DOCUMENT_MISSING    CLAIM_OUTSIDE_COVERAGE
KYC_VERIFICATION_FAILED    KYC_DOCUMENT_EXPIRED      KYC_ALREADY_VERIFIED

VALIDATION_FAILED          # generic 422
RESOURCE_NOT_FOUND         # generic 404
DUPLICATE_RESOURCE         # generic 409
RATE_LIMIT_EXCEEDED        # 429
INTERNAL_ERROR             # 500
```

### XVI. API Security Declaration Standards (NON-NEGOTIABLE)

Every endpoint MUST explicitly declare its security requirement — no implicit or
undeclared authentication state is permitted.

**Security schemes (declared in `components/securitySchemes`):**

```yaml
BearerAuth:
  type: http
  scheme: bearer
  bearerFormat: JWT
  description: JWT access token. Header: Authorization: Bearer <token>

ApiKeyAuth:
  type: apiKey
  in: header
  name: X-API-Key
  description: B2B/partner API key. Header: X-API-Key: <key>

TenantAuth:
  type: apiKey
  in: header
  name: X-Tenant-ID
  description: Tenant identifier for multi-tenant operations, alongside BearerAuth.
```

**Classification rules:**

- Global default in `openapi.yaml`: `security: [BearerAuth: []]` — protects all endpoints
  unless overridden.
- **Public endpoints** (no auth) MUST declare `security: []` explicitly:
  `/v1/auth/register`, `/v1/auth/email/register`, `/v1/auth/login`,
  `/v1/auth/email/login`, `/v1/auth/otp:send`, `/v1/auth/otp:verify`,
  `/v1/auth/otp:resend`, `/v1/auth/email/otp:send`, `/v1/auth/email/verify`,
  `/v1/auth/email/password:reset-request`, `/v1/auth/email/password:reset`,
  `/v1/auth/password:reset`, `/v1/auth/.well-known/jwks.json`,
  `GET /v1/products`, `GET /v1/products/{product_id}`, `GET /v1/products:search`.
- **Webhook endpoints** authenticate via HMAC signature in the request body/header;
  declare `security: []` and document the HMAC verification requirement.
- **Partner/B2B endpoints** requiring API key: declare `security: [ApiKeyAuth: []]`.
- **Tenant-scoped endpoints** requiring both JWT and tenant ID:
  declare `security: [BearerAuth: [], TenantAuth: []]`.
- SDK generators MUST read per-endpoint `security` to auto-inject correct auth headers.

### XVII. Pagination & List Standard (NON-NEGOTIABLE)

A single canonical pagination schema MUST be used across all list endpoints.
The schemas `PageResponse` and `PaginationResponse` are FORBIDDEN — replace with
`PaginationMeta` placed inside `ResponseMeta.pagination`.

**Request query parameters** (from Principle III):
`page` (integer, default 1), `page_size` (integer, max 100, default 20),
`sort_by` (string), `sort_order` (enum: asc|desc, default desc),
`search` (string).

**Canonical PaginationMeta schema:**

```yaml
PaginationMeta:
  type: object
  required: [page, page_size, total_pages, total_items, has_next, has_previous]
  properties:
    page:
      type: integer
      description: Current page (1-based)
    page_size:
      type: integer
    total_pages:
      type: integer
    total_items:
      type: integer
      format: int64
    has_next:
      type: boolean
    has_previous:
      type: boolean
    next_page_token:
      type: string
      nullable: true
      description: Cursor token for cursor-based pagination (optional)
```

**List response shape** — `data` MUST contain a named `items` key; bare arrays in `data`
are FORBIDDEN:

```json
{
  "success": true,
  "data": { "items": [...] },
  "error": null,
  "meta": { "request_id": "...", "pagination": { "page": 1, "page_size": 20, ... } }
}
```

### XVIII. DI-Ready API Contract (NON-NEGOTIABLE)

The API design MUST allow every portal and mobile app to:
1. Inject a single HTTP client with auth, retry, and logging as cross-cutting concerns.
2. Swap real API with mocks in tests using the same typed interface.
3. Use one generic response decoder for ALL endpoints (requires consistent envelope).
4. Write one error handler that works everywhere (requires standard error schema).
5. Generate fully type-safe SDKs with zero manual boilerplate.

**The five contract invariants (all MUST hold simultaneously):**

| Invariant | Requirement |
|-----------|-------------|
| Consistent envelope | ALL responses → `ApiResponse<T>{ success, data, error, meta }` |
| Correct status codes | `2xx` → unwrap `data`; `4xx/5xx` → unwrap `error`; `201` → cache-invalidate; `204` → no body |
| Per-endpoint security | `security: []` / `security: [BearerAuth]` / `security: [ApiKeyAuth]` declared on every endpoint |
| Standard error shape | `error.code` → switch/case; `error.field_violations` → form display; `error.retryable` + `retry_after_seconds` → retry logic |
| Standard pagination | `meta.pagination.{page, total_pages, has_next}` → universal list UI component |

The SDK generator (`api/generator/main.py`) MUST enforce all five invariants as CI gates.

### XIX. URL & Naming Standards (NON-NEGOTIABLE)

**URL structure rules:**

| Concern | Rule | Correct | Forbidden |
|---------|------|---------|-----------|
| Resources | Plural nouns | `/v1/policies` | `/v1/policy`, `/v1/getPolicies` |
| Custom actions | Colon notation (Google AIP-136) | `/v1/policies/{id}:cancel` | `/v1/cancelPolicy`, `/v1/policies/cancel/{id}` |
| Path casing | kebab-case | `/v1/audit-logs`, `/v1/api-keys` | `/v1/auditLogs`, `/v1/audit_logs` |
| Path parameters | snake_case | `{policy_id}`, `{user_id}` | `{policyId}`, `{id}` (too generic) |
| Query parameters | snake_case | `page_size`, `sort_by`, `from_date` | `pageSize`, `fromDate` |
| Versioning | URL prefix | `/v1/...`, `/v2/...` | Header versioning |
| Nesting depth | Max 2 levels | `/v1/policies/{id}/claims` | `/v1/users/{id}/policies/{id}/claims/{id}/docs` |

**JSON field naming — all request and response fields use `snake_case`:**

```json
{ "policy_id": "pol_123", "premium_amount": { "amount": "5000", "currency": "BDT" }, "created_at": "..." }
```
`camelCase` and `PascalCase` in JSON payloads are FORBIDDEN.

**Resource naming reference:**

| Resource | Collection | Single | Action |
|----------|-----------|--------|--------|
| Policy | `/v1/policies` | `/v1/policies/{policy_id}` | `/v1/policies/{policy_id}:cancel` |
| Claim | `/v1/claims` | `/v1/claims/{claim_id}` | `/v1/claims/{claim_id}:approve` |
| Payment | `/v1/payments` | `/v1/payments/{payment_id}` | `/v1/payments/{payment_id}:verify` |
| Order | `/v1/orders` | `/v1/orders/{order_id}` | `/v1/orders/{order_id}:cancel` |
| Product | `/v1/products` | `/v1/products/{product_id}` | `/v1/products/{product_id}:activate` |
| User | `/v1/users` | `/v1/users/{user_id}` | `/v1/users/{user_id}/sessions:revoke-all` |
| Quote | `/v1/quotes` | `/v1/quotes/{quote_id}` | `/v1/quotes/{quote_id}:approve` |
| KYC | `/v1/kyc-verifications` | `/v1/kyc-verifications/{kyc_id}` | `/v1/kyc-verifications/{kyc_id}:approve` |

**Nested resources** — nest only when the child has no standalone identity:
`/v1/users/{user_id}/policies`, `/v1/policies/{policy_id}/claims`,
`/v1/tickets/{ticket_id}/messages`. Flatten at 3+ levels.

### XX. Null, Empty & Optional Data Standards (NON-NEGOTIABLE)

**Rule 20.1 — Never omit declared fields; use explicit null:**
All fields declared in the schema MUST appear in every response. If absent, send `null` —
never silently omit. Omission causes `undefined` in TypeScript, nil panics in Swift,
and `NullPointerException` in Kotlin.

**Rule 20.2 — Action endpoints use `data: null`, not thin message objects:**
Endpoints that mutate state with no meaningful return value MUST return `data: null` in
the envelope. A `data` object containing only a `message` string is FORBIDDEN — messages
belong in `meta.message` when needed at all.

| Category | `data` value |
|----------|-------------|
| Creates resource | Full resource object |
| Returns computed result | Result object |
| Mutates + confirms | Updated resource (with status, timestamps) |
| Triggers side effect only | `null` |
| Validates/checks | Boolean / decision object |

**Rule 20.3 — Every schema field MUST be classified** as either:
- Member of the `required` array (always present, never null), **or**
- Annotated `nullable: true` (explicitly optional/null).

No field may exist in a schema without one of these declarations.

**Rule 20.4 — Specific thin-response endpoints MUST return structured data:**

| Endpoint | Correct `data` |
|----------|---------------|
| `POST /v1/auth/logout` | `null` |
| `POST /v1/auth/password:change` | `null` |
| `POST /v1/auth/otp:send` | `{ otp_id, expires_in_seconds }` |
| `POST /v1/auth/otp:verify` | `null` |
| `POST /v1/policies/{id}:cancel` | `{ policy_id, status, cancelled_at, refund_amount }` |
| `POST /v1/policies/{id}:issue` | `{ policy_id, status, issued_at, document_url }` |
| `POST /v1/claims/{id}:approve` | `{ claim_id, status, approved_at, settlement_amount }` |

## Development Workflow & Quality Gates

### Workflow

1. **Proto commit first** — new domain concept requires a proto file committed and
   `buf lint` + `buf breaking` passing before any service code is written.
2. **Run generation pipeline** — after every proto change:
   `scripts/generate.ps1` (Windows) or `scripts/generate.sh` (Linux/macOS).
   Pipeline order: `buf generate` → `inject_gorm_tags.go` → `api/generator/main.py`
   → SDK generation from `api/openapi.yaml`.
3. **Migration file (if schema change)** — write `ALTER TABLE` / `CREATE INDEX` only
   in `backend/inscore/db/migrations/`; verify no forbidden keywords are present;
   run `run_migration.ps1 --dry-run --Target=primary` and confirm zero zombie columns.
4. **Seed data (if needed)** — write `INSERT … ON CONFLICT` only in
   `backend/inscore/db/seeds/`; never in migration files.
5. **Feature spec and plan** — created via `/speckit.specify` and `/speckit.plan`
   before coding; Constitution Check table MUST be completed.
6. **Tests written (failing) first** — CI enforces test-before-merge with ≥ 80% coverage.
7. **Implementation uses VSA** — handler + domain logic + repository + GORM gateway
   in one cohesive slice; no cross-slice direct struct access.
8. **PR** requires: CI green, SAST clean (no CRITICAL), ≥ 1 peer review, constitution
   compliance checklist completed.
9. **Staging** triggers integration tests + migration dry-run + DAST (OWASP ZAP weekly).
10. **Production promotion** requires Grafana dashboard present and health probes passing.

### Quality Gates (blocking merge)

- `buf lint` clean — zero violations (STANDARD ruleset)
- `buf breaking --against .git#branch=main` clean — zero breaking changes within major version
- `scripts/generate.ps1 --dry-run` — no uncommitted diff in `gen/`, `api/openapi.yaml`,
  or `sdks/` (generated artefacts MUST be committed)
- Code freshness: no `*.pb.go` older than its `*.proto` source
- `run_migration.ps1 --dry-run --strict` — zero zombie columns, zero forbidden SQL keywords
- Build pass: `go build ./...`, `dotnet build`, `npm run build`
- Unit tests pass with ≥ 80% coverage
- SAST: zero CRITICAL findings (SonarQube / Checkmarx)
- No hand-edited files under `gen/` or `sdks/` (checked via `DO NOT EDIT` header scan)
- ClamAV scan clean for any document-upload flow changes
